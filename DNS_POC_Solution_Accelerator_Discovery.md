## 3. Zava Use Case — What the Accelerator Must Deliver

### 3.1 The Business Problem

Zava Energy runs aging **Bind DNS servers in their DMZ**. Only 2-3 engineers understand Bind. The servers require OS patching, config file management, and manual SIEM integration. Zava recently built an **Azure Enterprise Landing Zone** and wants to move DNS into Azure to:

1. **Eliminate DMZ risk** — remove DNS servers from the attack surface
2. **Democratize DNS management** — RBAC lets more team members manage records safely
3. **Automate certificate workflows** — DigiCert DCV via `_dnsauth` TXT records without manual steps
4. **Gain operational visibility** — query logging, dashboards, audit trails (today they have none)
5. **Enable future capabilities** — geo-routing, failover, load balancing (Bind can't do this)

### 3.2 Why This Is a Competitive Evaluation

Zava is evaluating **Azure DNS against at least one other vendor**. They're finishing the other vendor's POC first. Azure must be:
- **Faster to deploy** — hours, not days
- **Cleaner to demonstrate** — copy-paste scripts, not documentation-only
- **More compelling on integration** — native RBAC, Event Hub to QRadar, Monitor dashboards, Traffic Manager geo-routing... all first-party, no third-party connectors

### 3.4 Infrastructure Deployment Layers — Zava Greenfield

Since Zava is **greenfield** (no existing Azure DNS infrastructure), the accelerator must deploy everything from scratch in the correct dependency order.

#### Layer 0: Foundation (No dependencies — deploy first, parallel)

```
az group create  →  Resource Group (rg-dns-poc, southcentralus)
az monitor log-analytics workspace create  →  Log Analytics Workspace
az network dns zone create  →  Public DNS Zone (poc.Zava.com)
az network dns zone create  →  Private DNS Zone (poc-internal.Zava.local)
```

#### Layer 1: Observability + Messaging Platform (Depends on: Layer 0)

```
az eventhubs namespace create  →  Event Hub Namespace
az eventhubs eventhub create   →  Event Hub (dns-logs)
az monitor app-insights component create  →  Application Insights (per region)
```

#### Layer 2: Compute Endpoints (Depends on: Layer 0 + Layer 1)

```
az appservice plan create (Region A: southcentralus)  →  App Service Plan A
az appservice plan create (Region B: uksouth)          →  App Service Plan B
az webapp create (Region A)  →  Web App A (US endpoint)
az webapp create (Region B)  →  Web App B (UK endpoint)
az functionapp create (multi-region)  →  Function Apps for geo DNS testing
```

#### Layer 3: Traffic Routing (Depends on: Layer 2 — web apps must be running)

```
az network traffic-manager profile create (Priority)    →  Failover profile
az network traffic-manager profile create (Geographic)  →  Geo-routing profile
az network traffic-manager profile create (Weighted)    →  Load balancing profile
az network traffic-manager endpoint create (per profile, per webapp)
```

#### Layer 4: DNS Wiring (Depends on: Layer 0 + Layer 3)

```
az network dns record-set cname create  →  webdemo CNAME → TM FQDN
az network dns record-set txt create    →  asuid.webdemo → verification token
az network dns record-set txt create    →  _dnsauth → DCV test tokens
az network dns record-set txt create    →  _acme-challenge → ACME test tokens
az network dns record-set a create      →  Sample A, AAAA, MX, SRV, TXT records
Zone Import  →  az network dns zone import (Bind zone files)
```

#### Layer 5: Custom Domains + TLS (Depends on: Layer 4 — DNS must propagate)

```
az webapp config hostname add  →  Bind custom domain to each web app
az webapp config ssl create    →  Generate managed TLS certificate
az webapp config ssl bind      →  Enable HTTPS
```

#### Layer 6: Security, Compliance, Reporting (Depends on: Layers 0-5 operational)

```
az monitor diagnostic-settings create  →  DNS zone → Event Hub + LAW
az monitor diagnostic-settings create  →  Web Apps → LAW
az role definition create  →  Custom "DNS Record Operator" role
az role assignment create  →  Assign Operator + Admin roles
Azure Monitor Workbook deploy  →  Operational dashboards
```

#### Layer 7: Advanced / Optional (Depends on: full stack running)

```
az network dns dnssec-config create    →  DNSSEC signing
az network dns zone export             →  Snapshot automation
DCV proof suite (9 tests)              →  Certificate validation testing
Function App geo-probe tests           →  Multi-region nslookup emulation
```

## 4. Summary — From Discovery to Accelerator

### What We Learned from kimvaddi.com

1. **Core pattern is proven** — DNS Zone → CNAME → Traffic Manager → multi-region Web Apps → custom domain + TLS works end-to-end
2. **Performance routing works** — but Zava needs Priority (failover), Geographic, and Weighted profiles too
3. **App Service Managed Certificates work** — but Zava uses DigiCert CertCentral with `_dnsauth` DCV, which is a different workflow
4. **Logging gap is critical** — kimvaddi.com has zero diagnostic settings on the DNS zone, zero Event Hub, zero Workbooks. This is the #1 gap vs Zava's Required items
5. **Web apps work as TM endpoints** — even basic B1 plans are sufficient for POC health checks

### What Must Be Built New for Zava

1. **Event Hub + Diagnostic Settings** pipeline (Required #2: Audit Logging)
2. **Azure Monitor Workbook** templates (Required #3: Reporting)
3. **Zone snapshot automation** (Required #4: Zone Snapshots)
4. **DCV proof suite** — 9 tests for `_dnsauth` and `_acme-challenge` (Required #5: Certificate Integration)
5. **Custom RBAC role** definition and assignment (Scope: RBAC & Delegation)
6. **3 Traffic Manager profiles** with different routing methods (Optional #6, #7, #8)
7. **Multi-stage deployment orchestration** — Layers 0-7 with wait-gates for DNS propagation
